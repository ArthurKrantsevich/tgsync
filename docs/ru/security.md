# Безопасность

tgsync — это удалённый пульт для агента, который работает на твоём компьютере под твоим пользователем ОС. Кто управляет нодой, тот фактически может выполнять команды от твоего имени. Этот документ описывает, от чего tgsync защищает, от чего нет, и как настроить его аккуратно.

## Модель угроз

**Чему tgsync доверяет:**
- твоему аккаунту Telegram (его user_id в `ALLOWED_USER_IDS`);
- машине, на которой работает нода, и твоему пользователю ОС;
- Claude Code и настройкам в `~/.claude` (плагины, hooks, MCP-серверы работают как в терминале).

**От чего защищает:**
- посторонние пользователи Telegram не могут управлять нодой, даже если попали в группу;
- агент не выполняет необратимые или опасные действия без кнопки, если ты сам не включил автоодобрение;
- агент не читает и не отправляет в Telegram токен бота, пароль sudo и базу tgsync обычными инструментами;
- пароль sudo не попадает в окружение агента, его контекст, логи и базу.

**От чего не защищает:**
- от команды, которую ты одобрил, не прочитав: tgsync не песочница, одобренная команда выполняется с твоими правами;
- от кода, который агент может написать и запустить в режимах автоодобрения 🟢 и 🟡: он работает от твоего пользователя и видит всё, что видишь ты;
- от злоумышленника, который получил доступ к твоему аккаунту Telegram или к токену бота;
- от чтения переписки серверами Telegram: сообщения Bot API не шифруются end-to-end;
- от вредоносных плагинов, hooks и MCP-серверов в `~/.claude`.

## Кто может управлять

- Нода принимает сообщения и нажатия кнопок только от пользователей из `ALLOWED_USER_IDS`. Остальным она молча не отвечает.
- Нода работает только в своей группе (`GROUP_CHAT_ID`) и только в своих темах.
- Все участники группы видят весь вывод агента: команды, ответы, diff, присланные файлы. Не добавляй в группу людей и ботов, которым не доверяешь.
- Защити аккаунт Telegram: включи двухэтапную проверку (облачный пароль) и проверяй активные сеансы.

## Токен бота

- Токен даёт полный контроль над ботом. Храни его только в `.env` (права `0600`, файл в `.gitignore`).
- Нода убирает токен из окружения процесса `claude`, так что агент не получает его через переменные.
- Если токен попал в чат, лог или репозиторий, перевыпусти его: @BotFather → `/revoke` → выбери бота. Новый токен впиши в `.env` папки ноды (см. [ниже](#какие-данные-хранятся-и-где)) и перезапусти ноду.
- У каждой ноды свой бот. Утечка токена одной ноды не даёт доступа к другим машинам, но позволяет читать всё, что видит этот бот в группе.

## Что агент может в каждом режиме

Режим автоодобрения задаётся для всей ноды через `/approve` (подробнее — в [usage.md](usage.md#разрешения)).

| | 🔴 По запросу (по умолчанию) | 🟡 Всё, кроме sudo | 🟢 Всё сам |
|---|---|---|---|
| Читать и искать файлы | без вопросов | без вопросов | без вопросов |
| Править файлы внутри проекта | без вопросов, кроме [опасных файлов](#опасные-файлы-проекта) | без вопросов | без вопросов |
| Править файлы вне проекта | кнопка | без вопросов | без вопросов |
| Команды shell | кнопка, если нет правила «Всегда» | без вопросов | без вопросов |
| sudo (если `SUDO_MODE` не `off`) | кнопка | кнопка | без вопросов |
| Команды, которые могут трогать папку tgsync | кнопка без «Всегда» | кнопка без «Всегда» | кнопка без «Всегда» |
| Вопросы агента | кнопки | кнопки | кнопки |

Во всех режимах без вопросов разрешено то, что разрешено в твоих настройках Claude Code (`~/.claude/settings.json`, настройки проекта). Проверь, что там нет широких правил, которые ты не готов доверить агенту без присмотра.

**Что это значит на практике.** В режимах 🟡 и 🟢 агент может выполнить любой код от твоего пользователя: удалить файлы, отправить данные в сеть, прочитать ключи SSH. Включай их только для проектов и задач, которым доверяешь, и возвращай 🔴, когда не следишь за работой. В 🟢 с включённым sudo агент получает root без подтверждения.

`/mode acceptEdits` (режим самого Claude Code) разрешает правки файлов без вопросов на стороне Claude Code. В этом режиме проверки tgsync для отдельных файлов могут не вызываться, поэтому для работы с чужим или непроверенным кодом оставляй `default`.

## Служебные файлы tgsync

Служебные файлы — это `.env` (токен бота, пароль sudo) и база SQLite (`tgsync.db` и её `-wal`/`-shm`).

- Инструменты чтения, записи и поиска, указывающие на эти файлы или в их папку, отклоняются.
- Команда shell с буквальным путём к `.env` или базе отклоняется, в том числе с sudo.
- Команда shell, которая может обращаться к папке tgsync другим способом (`~` и `$HOME`, относительные пути, маски вроде `tgs*`, переменные перед `/tgsync/`, вложенные `sh -c` и heredoc, а также папки выше, например `~` или `/`), приходит кнопкой без «Всегда» в любом режиме автоодобрения, и сохранённые правила на неё не действуют. Читай такие команды внимательно.
- `send_file`, `/file`, `/ls` и diff хода не отправляют служебные файлы, даже если они лежат в проекте.

**Ограничение.** Агент работает под тем же пользователем ОС, поэтому это правила tgsync, а не права ОС. Это дополнительная защита, а не граница: скрипт, который агент напишет и запустит (в режимах 🟡 и 🟢 — без вопросов), может прочитать эти файлы, и tgsync этого не увидит.

## Опасные файлы проекта

Некоторые файлы проекта заставляют git, Claude Code или shell выполнять команды: `.git/` (config, hooks), `.gitattributes`, `.gitmodules`, `.claude/`, `.envrc` на любой глубине, `.mcp.json` и `.vscode/tasks.json` в корне проекта. tgsync сам запускает `git add` для снимков хода, а это запускает фильтры из `.gitattributes`.

Поэтому в режиме 🔴 правка таких файлов приходит кнопкой даже внутри проекта, без «Всегда», и сохранённые правила на неё не действуют. Симлинки раскрываются: файл, который ссылка уводит за пределы проекта или в один из этих путей, тоже требует кнопки.

## Кнопка «Всегда»

- Для shell запоминается команда с первым аргументом (`go test`). Цепочки, подстановки и перенаправления под правило не подходят.
- Для shell и интерпретаторов, `rm`, `dd`, `chmod`, `find`, обёрток (`env`, `xargs`, `eval`, `timeout` …), `ssh`, `sudo`, команд с `VAR=value` впереди и `git` с глобальными опциями кнопки «Всегда» нет. Старые правила вроде `python3` или `rm` на них больше не действуют.
- Правило `npm run` или `make` разрешает любой скрипт или цель, поэтому выбирай «Всегда» для узких команд.
- Для правки файла вне проекта правило действует только на папку этого файла, без подпапок; старые правила без папки больше не действуют.
- Правила хранятся в базе для каждого проекта отдельно.

## sudo

Bash агента работает без терминала, поэтому `sudo` не может спросить пароль сам. tgsync даёт ему askpass-мост:

1. Агент хочет выполнить команду с `sudo` — в теме появляется запрос «🔐 sudo» с командой и кнопками ✅/❌. Кнопки «Всегда» нет.
2. После ✅ tgsync находит в команде настоящие вызовы `sudo` (shell-парсером, а не поиском по тексту) и превращает каждый в `TGSYNC_SUDO_TOKEN=<одноразовый токен> sudo -A …`. Токен действует только для этих вызовов, 5 минут и до конца хода. sudo через обёртки (`env`, `xargs`, `find -exec`, `sh -c`) не поддерживается: агента попросят переписать команду.
3. `sudo` запускает `tgsync` как `SUDO_ASKPASS`. Тот передаёт токен ноде через unix-сокет `askpass.sock` (права 0600). Нода отдаёт пароль, только если токен действителен и к сокету подключился процесс, запущенный `sudo`: родитель должен называться `sudo` и работать с эффективным uid 0, как настоящий setuid-sudo (на Linux — через `SO_PEERCRED` и `/proc/<pid>/status`, на macOS — через `LOCAL_PEERPID` и `sysctl`).

Режимы (`SUDO_MODE` в `.env`):

| Режим | Откуда пароль | Риски |
|---|---|---|
| `off` (по умолчанию) | sudo отклоняется | нет |
| `env` | `SUDO_PASSWORD` из `.env`; нода убирает его из окружения агента | пароль лежит на диске открытым текстом (права 0600); агент под тем же пользователем технически может прочитать файл, tgsync запрещает это только правилами |
| `telegram` | после ✅ бот просит пароль в теме и сразу удаляет сообщение | пароль проходит через серверы Telegram и до удаления виден другим ботам группы; боту нужно право «Удаление сообщений» (`tgsync check` это проверяет) |

В режиме `telegram` пароль спрашивается на каждую команду: без терминала sudo не кеширует вход. Несколько вызовов sudo в одной одобренной команде получают один ответ; при опечатке sudo спросит снова, до 3 попыток на вызов. Неверный пароль считается неудачной попыткой входа (`pam_faillock` может заблокировать учётную запись).

Что важно понимать:
- Одобренная sudo-команда получает права root. Защита — это кнопка: читай команду целиком перед ✅. Другие части той же команды (например, `./configure` в `./configure && sudo make install`) токен не видят, но выполняются от твоего пользователя.
- В режиме автоодобрения 🟢 sudo-команды выполняются без кнопки.
- Не задавай `SUDO_PASSWORD` через `Environment=` в systemd или `environment:` в compose: оттуда он виден в `/proc/<pid>/environ`.
- Надёжнее пароля — правило `NOPASSWD` в `/etc/sudoers.d/` только для нужных команд (например, `systemctl restart myapp`), при `SUDO_MODE=off` для остального.
- Команды, которые трогают служебные файлы tgsync, отклоняются и с sudo.

## Какие данные хранятся и где

Папка ноды: `~/.config/tgsync` на Linux, `~/Library/Application Support/tgsync` на macOS, `%APPDATA%\tgsync` на Windows (или `TGSYNC_HOME`).

| Что | Где | Содержимое |
|---|---|---|
| `.env` | папка ноды, права 0600 | токен бота, id пользователей и группы, настройки, пароль sudo в режиме `env` |
| `profiles.yaml` | папка ноды | профили плагинов |
| база SQLite | `DB_PATH` (по умолчанию `data/tgsync.db` в папке ноды) | сессии и их темы, правила «Всегда», режим автоодобрения, расход токенов, состояние лимитов подписки, id служебных сообщений темы ноды |
| входящие файлы | `.tgsync/inbox/` в проекте | файлы, которые ты прислал агенту; исключены из git через `.git/info/exclude` |
| снимки ходов | объекты git в репозитории проекта | деревья рабочего каталога до и после хода; ветки, индекс и stash не меняются, недостижимые объекты убирает `git gc` |
| логи | journald (`journalctl --user -u tgsync`), `~/Library/Logs/tgsync.log` на macOS, файл `TGSYNC_LOG` на Windows | события ноды и ошибки; могут содержать пути, команды и тексты ошибок — просматривай перед тем, как делиться |

История разговоров хранится самим Claude Code в `~/.claude`, как для сессий из терминала. tgsync её читает (для `/history`), но не копирует.

## Что уходит в Telegram

В тему сессии уходят: твои задачи, ответы агента, его текущие действия (команды shell, пути файлов), запросы разрешений с командами, вопросы, списки изменённых файлов, diff и файлы, которые ты запросил или которые подходят под `AUTO_SEND_GLOBS`, расшифровки голосовых, результаты субагентов. Всё это хранится на серверах Telegram и видно всем участникам группы.

Не проси агента выводить секреты в чат и следи за `AUTO_SEND_GLOBS`: маска `**/*` отправит всё, что агент изменил.

## Внешние сервисы

tgsync обращается только к:
- **Telegram Bot API** — для работы бота;
- **Claude Code** — локальный CLI `claude`, который сам общается с Anthropic, как в терминале;
- **серверу распознавания речи** по `STT_URL`, если он задан.

Других сервисов ИИ, аналитики и телеметрии нет. Распознавание речи рассчитано на свой сервер (готовый `deploy/stt/compose.yaml` слушает только `127.0.0.1`). Если укажешь в `STT_URL` чужой сервис, голосовые будут уходить туда — это противоречит замыслу проекта.

## Windows и Docker

- Права 0600/0700 на Windows не действуют. `.env` и база защищены только правами профиля пользователя: `%APPDATA%` доступен тебе и администраторам.
- На Windows sudo нет: `SUDO_MODE` принудительно `off`, сокет не создаётся.
- В контейнере из `Dockerfile` нет sudo, держи `SUDO_MODE=off`. Контейнер работает под твоим uid и видит `~/.claude` и `PROJECTS_ROOT` — это не изоляция агента от твоих файлов.

## Как сообщить об уязвимости

Не открывай публичный issue. Используй приватный отчёт на GitHub, как описано в [SECURITY.md](../../SECURITY.md).
