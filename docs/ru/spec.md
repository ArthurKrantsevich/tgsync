# tgsync — техническая спецификация

Документ описывает tgsync в том виде, в каком он реализован в текущем коде
(`cmd/tgsync`, `internal/*`, `scripts/*`, `Dockerfile`, `.env.example`). Если
документ и код расходятся, прав код.

Все идентификаторы ниже — условные: группа `-1001234567890`, пользователь
`123456789`, домашняя папка `/home/user`, бот `ExampleNodeBot`.

---

## 1. Назначение, границы, что не входит

### Назначение

tgsync позволяет одному человеку управлять сессиями агента Claude Code на
своих компьютерах из Telegram. На каждом компьютере работает *нода* — один
процесс на Go. Она запускает Claude Code через Go Agent SDK, показывает ход
работы агента в форум-группе Telegram и превращает запросы разрешений и
вопросы агента в inline-кнопки.

### Что входит

- Одна супергруппа Telegram с включёнными темами, общая для любого числа нод.
- У каждой ноды — тема управления с закреплённой карточкой и по теме на каждую
  сессию агента.
- Новые сессии в проектах из заданной корневой папки и продолжение сессий
  Claude Code, начатых в другом месте (терминал, десктоп-приложение).
- Одобрение вызовов инструментов, ответы на `AskUserQuestion`, панель
  субагентов, отчёты о контексте и расходе, уведомления о лимитах подписки.
- Итоги хода на основе git-снимков: diff, коммит, откат.
- Обмен файлами в обе стороны; голосовые через собственный сервер
  распознавания речи.
- Необязательный `sudo` для агента с одобрением каждой команды.

### Что не входит

- Многопользовательский режим. Нода полностью доверяет каждому пользователю
  из `ALLOWED_USER_IDS`; ролей нет.
- Песочница для агента. Агент работает от пользователя ОС, под которым
  запущена нода, с его правами. Проверки tgsync снижают риск ошибок, но не
  являются границей изоляции (см. §5.9).
- Обращения к сторонним AI- и speech-сервисам. Модель вызывает локальный
  Claude Code CLI; распознавание речи идёт только на сервер, который
  разворачивает сам оператор.
- Веб-интерфейс, публичный API, связь между нодами. Ноды не общаются друг с
  другом, у них только общая группа в Telegram.

## 2. Понятия

| Термин | Значение |
|---|---|
| **Нода** | Один процесс `tgsync` на одной машине со своим токеном бота, `.env`, базой SQLite и темой управления. Имя — `NODE_NAME` (по умолчанию hostname). |
| **Группа** | Супергруппа Telegram с темами (`GROUP_CHAT_ID`, например `-1001234567890`). В одной группе может быть несколько нод, у каждой свой бот. |
| **Тема управления** | Собственная тема ноды с именем `🖥 <нода>`. В ней карточка, меню и команды уровня ноды. Id хранится в `kv.control_thread_id`; удалённая тема создаётся заново. |
| **Карточка** | Закреплённое сообщение в теме управления: имя ноды, число открытых и закрытых сессий, «онлайн с», кнопки 🧹 Уборка и 🧽 Очистить тему. Обновляется каждые 10 с при изменении текста и не реже раза в минуту. |
| **Тема сессии** | По теме на каждую сессию агента, имя `<проект> · <заголовок>` (≤128 единиц UTF-16). Иконка показывает состояние (💻 активна, ✅ закрыта, ❌ упала, с запасными вариантами). |
| **Проект** | Папка прямо внутри `PROJECTS_ROOT` с именем по шаблону `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. Рабочая папка сессии. `/newproject` создаёт её и выполняет `git init`. |
| **Профиль** | Именованный набор настроек Claude Code из `profiles.yaml`: `setting_sources`, `env` и переопределение `settings`, которое передаётся через `--settings`. Встроенный профиль `full` берёт `user, project, local`. Выбирается по `--profile`, затем по `projects.<имя>.profile`, затем по `DEFAULT_PROFILE`. |
| **Ход** | Один цикл ответа агента: промпт отправлен, идут события, событие result его завершает. *Продолжение* — ход, который CLI начинает сам, когда закончил фоновый субагент. |
| **Входящие / очередь** | У каждой сессии — FIFO сообщений пользователя, ждущих следующего хода. На уровне ноды — FIFO тем, ждущих свободного слота (`MAX_PARALLEL_SESSIONS`, и не больше одного хода на проект). |
| **Состояние сессии** | `queued`, `starting`, `running`, `waiting` (ждёт пользователя), `idle`, `interrupted`, `failed`, `closed`. Хранится в `sessions.state`. |
| **Режим разрешений** | Собственный режим Claude Code для сессии: `default`, `acceptEdits`, `plan` (меняется командой `/mode`). Передаётся в CLI. |
| **Режим автоодобрения** | Настройка tgsync на всю ноду (`/approve`): `ask` (🔴 кнопка на каждый запрос), `nosudo` (🟡 всё, кроме sudo, разрешается само), `all` (🟢 всё, включая sudo). Хранится в `kv.approve_mode`, по умолчанию `ask`. |
| **Правило «Всегда»** | Сохранённое разрешение для проекта, создаётся кнопкой «♾ Всегда», хранится в `permission_rules`. |

### 3.2 Модель процесса

Нода — один процесс ОС. Горутины:

| Горутина | Кто запускает | Что делает |
|---|---|---|
| Long polling | `api.Run` (главная горутина) | `getUpdates` с `allowed_updates = [message, callback_query]`. Обработчики выполняются синхронно в этой горутине и только передают апдейт диспетчеру. |
| Обработчик темы | диспетчер, по одной на тему с очередью | Обрабатывает сообщения одной темы в порядке прихода (буфер 256). Завершается, когда очередь пуста. Долгое действие (например, распознавание голосового) задерживает только следующие сообщения этой же темы. |
| Обработчик кнопки | диспетчер, по одной на нажатие | Нажатия идут мимо очереди темы, чтобы кнопки отвечали, пока обрабатывается сообщение. |
| Тикер менеджера сессий | `mgr.Run` | Каждые 3 с (`EditInterval`): остановка простаивающих процессов, предупреждения о тишине, `MAX_TURN_DURATION`, напоминания о запросах, обновление статусов и открытых карточек агентов. Каждые 10 мин: проверка, не удалены ли темы простаивающих сессий. |
| Чтение событий | по одной на процесс Claude | `readEvents` читает канал событий агента и ведёт сессию. |
| Насос SDK | по одной на процесс Claude | Читает ответы SDK ход за ходом и превращает их в события (буфер канала 256). |
| Доставка файлов | по одной на законченный ход | Отправляет файлы и итог хода после освобождения слота. |
| Уведомления таймеров | по одной на тик, если есть работа | Шлёт предупреждения о тишине и прерывает слишком долгие ходы, не задерживая тикер. |
| Тикер группы | `grp.Run` | Каждые 10 с — обновление карточки. Каждую минуту — удаление сообщений темы управления старше часа. |
| Сервер askpass для sudo | `sudoSrv.Serve`, только если `SUDO_MODE` не `off` | Принимает соединения на unix-сокете, по горутине на соединение. |
| Обработка сигналов | `run` | Первый SIGINT/SIGTERM отменяет корневой контекст; второй завершает процесс сразу. |

У трекера лимитов своей горутины нет: его вызывает обработка событий сессии.

### 3.3 Поток данных: сообщение пользователя → ход агента → вывод в Telegram

1. **Приём.** Long polling приносит апдейт. `normalize` отбрасывает апдейты
   из других чатов и от ботов и достаёт id пользователя, id темы
   (0 — General), текст или подпись, документ/фото, голосовое/аудио или
   данные кнопки.
2. **Диспетчеризация.** Сообщения идут в упорядоченную очередь темы, кнопки
   обрабатываются сразу. Паника в обработчике перехватывается и пишется в лог.
3. **Авторизация.** `Router.Handle` игнорирует пользователей не из
   `ALLOWED_USER_IDS`.
4. **Маршрут.** General — только `/control`. Тема управления — команды и
   меню ноды. Тема, принадлежащая сессии этой ноды, — обработка сессии.
   Любая другая тема принадлежит другой ноде и игнорируется.
5. **Текст в сессии.** По порядку: если ждём пароль sudo, текст считается
   паролем (сообщение удаляется); известные команды сессии выполняются; если
   вопрос ждёт «✍ Свой ответ», текст становится ответом; иначе текст уходит в
   `Manager.MessageFrom`.
6. **Очередь.** На сообщение ставится реакция 👀, оно добавляется во входящие
   сессии (с префиксом — списком файлов, присланных без подписи). Сессия с
   заголовком `новая сессия` переименовывается по первой строке текста
   (≤40 символов). Если ход идёт или стоит в очереди, публикуется уведомление
   «📥 В очереди» с кнопкой «⚡ Отправить сейчас».
7. **Планирование.** `schedule` берёт первую тему из очереди, в проекте
   которой сейчас нет хода, пока идёт меньше `MAX_PARALLEL_SESSIONS` ходов.
   Остальные получают состояние `queued`.
8. **Старт.** Если у сессии нет процесса Claude, он запускается (§4.1) с
   продолжением `claude_session_id`, если он есть. Делается git-снимок
   проекта (§6). Публикуется статус-сообщение с ⏹, состояние — `running`.
   Промпт отправляется агенту (с пометкой об откате, если прошлый ход
   откатили).
9. **Поток событий.** События обновляют статус-сообщение (не чаще раза в
   3 с; при смене состояния ожидания — сразу): счётчик шагов, текущий
   инструмент, строка субагента, последняя реплика агента. Полностью
   публикуется только финальный текст хода; промежуточные становятся
   заметкой в статусе.
10. **Разрешения.** Вызовы, о которых CLI спрашивает, идут в `CanUseTool`
    (§4.3, §5).
11. **Конец хода.** По событию result: открытые запросы темы снимаются,
    состояние — `idle`, статус-сообщение удаляется (или редактируется, если
    удалить не вышло), реакция 👀 снимается, ответ отправляется частями,
    строка итога (`✅ Ход завершён · время · шагов · $стоимость`) с кнопкой `⋯`
    добавляется к последней части или идёт отдельным сообщением. Расход
    записывается. Планируется следующий ход из очереди. Файлы доставляются в
    фоне. Затем запрашивается заполненность контекста (таймаут 5 с), и к
    строке итога добавляется `· 🧠 N%`; может прийти подсказка о сжатии.

## 4. Интеграция с агентом

### 4.1 Запуск Claude Code

`agent.SDKRunner` использует `github.com/ProjAnvil/claude-agent-sdk-golang`.
Процесс живёт на собственном контексте и не зависит от запроса Telegram,
который его запустил.

| Параметр | Значение |
|---|---|
| CLI | `claude` из `PATH` или `CLAUDE_CLI_PATH` |
| Рабочая папка | папка проекта |
| Продолжение | `sessions.claude_session_id`, если задан; с `Fork` (подключение сессии, активной в другом месте) опция fork-session в SDK продолжает копию под новым id |
| Режим разрешений | `sessions.mode` (`default` / `acceptEdits` / `plan`) |
| Источники настроек | из профиля; `full` = `user, project, local` |
| `--settings` | карта `settings` профиля в JSON, если есть |
| Окружение | `env` профиля, затем переменные askpass для sudo (§5.8) |
| Системный промпт | пресет `claude_code` с дописанным промптом tgsync (ниже) |
| События hooks | включены при `SHOW_HOOK_OUTPUT=true` |
| MCP-сервер | встроенный SDK-сервер `tgsync` с одним инструментом `send_file` |
| Буфер | 16 МиБ на сообщение SDK |

До запуска любого агента нода удаляет `TELEGRAM_BOT_TOKEN` и `SUDO_PASSWORD`
из своего окружения, поэтому ни Claude, ни запущенные им инструменты их не
наследуют.

**Дописанный системный промпт.** Агенту сообщается, что им управляют из
Telegram; что для документов, которые пользователь должен прочитать, нужно
вызывать `mcp__tgsync__send_file`; что полностью публикуется только последнее
сообщение хода, поэтому оно должно быть коротким и начинаться с результата; и
что `description` у Bash показывается рядом с командой в запросе
разрешения, поэтому там нужно кратко, на языке пользователя, объяснить,
зачем команда запускается. Если sudo включён, агенту также сообщается, что
sudo работает через одобрение в Telegram и `SUDO_ASKPASS`, и что проверять
доступ через `sudo -n` не нужно.

**Инструмент `send_file`.** Аргументы: `path` (обязателен, относительно
проекта или абсолютный внутри него) и `caption`. Загружает файл в тему сессии
(§7). Уже отправленная версия (тот же SHA-256) повторно не отправляется,
инструмент сообщает об этом.

### 4.2 Обрабатываемые события

| Сообщение SDK | Событие | Обработка |
|---|---|---|
| `system/init` | `Init` | Сохраняет id сессии Claude; запоминает slash-команды для `/skills`; один раз за жизнь объекта сессии сообщает о MCP-серверах со статусом не `connected` и не `pending`. |
| `system/compact_boundary` | `Compacted` | Пишет «🗜 История сжата (авто/вручную), было N»; сбрасывает снимок контекста. |
| событие лимита | `RateLimit` | Передаётся трекеру лимитов (§4.7). |
| task started / progress / notification / terminal update | `TaskStarted`, `TaskProgress`, `TaskDone` | Панель субагентов (§4.5). Учитываются только `local_agent`, `local_workflow` и задачи без типа; shell-задачи игнорируются. |
| текст ассистента | `Text` | Только верхний уровень: сохраняется как отложенный текст; становится заметкой статуса при следующем вызове инструмента или публикуемым ответом в конце хода. Текст субагентов не публикуется. |
| вызов инструмента | `ToolUse` | Строка статуса; учёт изменённых файлов; вызовы Agent/Task запоминаются для панели. |
| ошибка ассистента | `Error` | Публикуется как `⚠️ …`. |
| результат инструмента | `ToolResult` | Для вызовов Agent сохраняется текст результата для панели. |
| ответ hook | `Hook` | `systemMessage` hook'а или короткая заметка о сбое (stderr ≤300 символов), публикуется как `🪝 …`, если включено. Добавленный hook'ом контекст не показывается. |
| result | `Result` | Завершает ход (§3.3, шаг 11). |

Если `Text`, `ToolUse` или непустой `Result` верхнего уровня приходит, когда
хода нет, начинается **продолжение**: у него есть статус-сообщение и
стартовый снимок, но слот `MAX_PARALLEL_SESSIONS` оно не занимает (ход уже
идёт в CLI). Result без текста и без ошибки вне хода игнорируется.

Когда канал событий закрывается (CLI завершился), открытые запросы
снимаются, работающие субагенты помечаются остановленными, а если шёл ход,
состояние становится `failed` с уведомлением. Следующее сообщение запускает
новый процесс, который продолжает сессию.

### 4.3 Обратный вызов разрешений (`CanUseTool`)

Каждый запущенный процесс получает обратный вызов, привязанный к своей
сессии (тема, проект, папка проекта, защищённые пути). На каждый вызов,
который передаёт CLI:

1. `AskUserQuestion` → поток вопросов (§4.4). Режимы автоодобрения на него не
   влияют.
2. Иначе `permissions.Evaluate` возвращает `Allow`, `Deny`, `Ask` или
   `Confirm` с учётом сохранённых правил проекта (§5.3).
3. `Allow` → разрешено. `Deny` → отказ с причиной, которую видит агент;
   исключение — sudo-команда при включённом sudo: она превращается в запрос
   одобрения.
4. Для sudo команду сначала пробно переписывают; если её вызовы sudo
   переписать нельзя (например, sudo спрятан за `env`, `xargs`, `sh -c`), она
   отклоняется с объяснением.
5. Если решение не `Confirm` и режим автоодобрения это позволяет (`all`, или
   `nosudo` для не-sudo запросов), вызов разрешается, а в тему тихо уходит
   заметка «✅ авто: …».
6. Иначе публикуется запрос: имя инструмента, заголовок; для Bash — описание
   (≤300 символов) и команда (≤700); для Edit — путь и старая/новая строки
   (≤350 каждая); для Write — путь и содержимое (≤700); для остальных —
   входные данные в JSON (≤700). Кнопки: ✅ Разрешить, ❌ Отклонить и
   ♾ Всегда: `<правило>`, если правило можно построить и запрос не sudo и не
   `Confirm`.
7. Вызов блокируется, пока не нажата кнопка, не закончился ход, не
   завершился процесс или не закрыта сессия. На время ожидания состояние
   сессии — `waiting`.

При отказе пользователя агенту сообщается, что причину пользователь может
написать следующим сообщением.

### 4.4 `AskUserQuestion`

- Вопросы из `questions` показываются по одному: заголовок (если есть),
  текст, «Вопрос i из n».
- Одиночный выбор: кнопка на каждый вариант; нажатие — ответ.
- Множественный выбор: переключатели (☐/☑) и «Готово»; нужно выбрать хотя бы
  один вариант.
- У каждого вопроса есть «✍ Свой ответ»: следующее текстовое (или
  распознанное голосовое) сообщение в теме становится ответом.
- После последнего ответа вызов разрешается с `UpdatedInput` = исходные
  данные плюс `answers` (текст вопроса → ответ, несколько вариантов через
  «, »).
- Вход без разбираемых вопросов разрешается без изменений.

### 4.5 Панель субагентов

- Вызов `Agent`/`Task` запоминает `subagent_type` (по умолчанию `agent`) и
  вызывающего. Когда стартует соответствующая задача, она добавляется в
  панель сессии. Несопоставленные вызовы старше 10 минут забываются.
- Новое сообщение панели начинается, когда стартует задача, а в прежней
  панели нет работающих агентов; у старой панели пропадают кнопки.
- **Список:** сначала работающие, затем недавно завершённые, не больше 12,
  деревом под вызвавшими агентами; остальные показываются числом. По кнопке
  на каждого показанного агента (по 3 в ряд) — открыть карточку.
- **Карточка:** имя, описание, состояние, кто вызвал, текущее действие
  (последний вызов инструмента субагента), итог (≤1000 символов), время
  старта, длительность, число вызовов инструментов. Кнопки: ⬅ Назад;
  ⏹ Остановить (`StopTask`), пока агент работает; 📄 Результат после
  завершения — последний текст ассистента из журнала задачи (читаются только
  последние 8 МиБ) или результат инструмента; отправляется файлом
  `agent-<имя>-<n>.md`.
- Правки панели ограничены по частоте так же, как статус; открытая карточка
  работающего агента обновляется тикером.
- `/agents` публикует панель заново внизу темы.
- `/stop` субагентов не останавливает, а сообщает, сколько их ещё работает.
  При закрытии сессии все работающие агенты останавливаются. При завершении
  процесса они помечаются остановленными.
- Пока работает хоть один агент, `IDLE_TIMEOUT` процесс не останавливает.

### 4.6 Контекст и расход

- **Расход.** CLI сообщает накопленный расход по моделям за жизнь процесса.
  На каждом result нода сохраняет разницу с прошлыми итогами (если итог
  уменьшился, например после `/clear`, он учитывается целиком) строками в
  `usage` (input, output, чтение кэша, создание кэша, стоимость).
- **Контекст.** После каждого хода запрашивается `GetContextUsage` (таймаут
  5 с). Процент добавляется к строке итога.
- **Подсказка о сжатии.** Когда контекст переходит 70 % — или на 10 пунктов
  ниже порога автосжатия, если он ниже, — один раз на каждое пересечение
  приходит подсказка с кнопкой 🗜 Сжать. Кнопка ставит в очередь `/compact`
  (без дублей).
- `/context` показывает модель, итоги, разбивку по категориям и порог
  автосжатия; без живого процесса — последний снимок с пометкой, что он
  устарел.
- `/usage` в теме сессии: ходы, токены, чтения кэша, стоимость, последняя
  заполненность контекста. В теме управления: окна лимитов подписки и итоги
  по проектам за сегодня и за 7 дней.

### 4.7 Лимиты подписки

- Окна: `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`,
  `overage`. Статусы: `allowed`, `allowed_warning`, `rejected`.
- Каждое событие сохраняется в `rate_limits`. Уведомления не повторяются для
  той же пары `статус|время сброса`; это состояние восстанавливается из базы
  при старте.
- `allowed_warning` → тихое уведомление с процентом и временем сброса;
  `rejected` → уведомление со звуком; `allowed` после `rejected` → «✅ снова
  доступен» только в теме управления. Предупреждения и исчерпание приходят в
  тему сессии, где случились, и в тему управления. Если в тему управления
  отправить не удалось, попытка повторится на следующем событии.
- Событие без имени окна: предупреждение или исчерпание показывается, но не
  сохраняется; безымянный `allowed` снимает все ограниченные окна.

## 5. Разрешения и модель безопасности

### 5.1 Кто управляет нодой

- Апдейты из чатов, кроме `GROUP_CHAT_ID`, и от ботов отбрасываются.
- Апдейты от пользователей не из `ALLOWED_USER_IDS` молча игнорируются.
- Каждый разрешённый пользователь имеет полный доступ; ролей нет.
- Кнопки дополнительно проверяют, что их нажали в своей теме; устаревшие
  отвечают «Кнопка устарела» / «Запрос устарел».

### 5.2 Защищённые файлы tgsync

Защищены абсолютные пути `.env`, базы данных и её файлов `-wal` и `-shm`.
Для них:

- **отказ** для Bash-команд, где путь встречается буквально (на Windows также
  с `/`, двойными слэшами и в форме Git Bash `/c/…`; без учёта регистра на
  Windows и macOS);
- **отказ** для файловых инструментов (`file_path`, `notebook_path`),
  указывающих на файл, — сравнение после нормализации и по идентичности файла
  (жёсткие и символические ссылки);
- **отказ** для инструментов с аргументом `path` внутри защищённого пути;
- они никогда не отправляются (`send_file`, `/file`, `/ls`, автоотправка,
  diff) и скрыты в `/ls`.

### 5.3 Правила (`Evaluate`)

По порядку:

1. **Bash:** упомянут защищённый путь → `Deny`. Вызов sudo (разбирается
   парсером shell, включая `env sudo`, `xargs sudo`, `find -exec sudo` и
   скрипты `sh -c`; для неразбираемых команд — регулярное выражение) →
   `Deny` с причиной «sudo выключен» (брокер превращает её в запрос, если
   sudo включён). Команда, которая может обращаться к папке tgsync (§5.5) →
   `Confirm`.
2. Защищённый файл или путь в аргументах → `Deny`.
3. Инструменты только для чтения (`Read`, `Glob`, `Grep`, `LS`,
   `NotebookRead`, `TodoWrite`, `Task`, `Agent`, `Skill`,
   `mcp__tgsync__send_file`) → `Allow`.
4. Инструменты записи (`Edit`, `MultiEdit`, `Write`, `NotebookEdit`):
   - чувствительная запись (§5.4) → `Ask`;
   - цель внутри проекта после разрешения символических ссылок → `Allow`;
   - цель прямо в папке, сохранённой правилом «Всегда» для этого инструмента
     (по имени и после разрешения ссылок) → `Allow`;
   - иначе → `Ask`.
5. Остальные инструменты: подходящее сохранённое правило → `Allow`, иначе
   `Ask`.

`Confirm` требует кнопку в любом режиме автоодобрения, не предлагает
«Всегда», и сохранённые правила на него не действуют.

### 5.4 Чувствительные записи

Запись чувствительная, если путь — по имени или после разрешения ссылок —
внутри проекта и:

- содержит компонент `.git` или `.claude` на любом уровне;
- называется `.gitattributes`, `.gitmodules` или `.envrc` на любой глубине;
- это `.mcp.json` в корне проекта или `.vscode/tasks.json`.

Такие файлы заставляют git, Claude Code, direnv или редактор выполнять
команды (сам tgsync вызывает `git add` для снимков, а он запускает clean-
фильтры). Чувствительная запись — это `Ask`: правило проекта её не
разрешает, кнопки «Всегда» нет. **Важно:** `Ask` в режимах 🟢 и 🟡 всё равно
разрешается автоматически.

### 5.5 Проверка обращений к папке tgsync (дополнительный рубеж)

Для Bash `reachesTgsync` ищет написания папки tgsync, которые пропускает
буквальная проверка: `~` и `$HOME`, относительные пути, маски, переменные
(`$X/tgsync/.env`), формы `--opt=путь` и `VAR=путь`, вложенные скрипты
`sh -c` и heredoc (до глубины 3), а также хвосты `папка/файл` вроде
`tgsync/.env`. Пути внутри проекта не учитываются, если папка tgsync сама не
лежит в проекте. Совпадение делает запрос `Confirm`. Для sudo-команд
совпадение тоже требует кнопку.

### 5.6 Режимы автоодобрения

| Режим | Значение | Поведение |
|---|---|---|
| 🔴 По запросу | `ask` (по умолчанию) | На каждый запрос `Ask` — кнопки. |
| 🟡 Всё, кроме sudo | `nosudo` | Запросы `Ask` разрешаются сами с тихой заметкой «✅ авто»; на sudo — кнопки. |
| 🟢 Всё сам | `all` | Запросы `Ask` и sudo разрешаются сами (для sudo всё равно нужен пароль). |

Во всех режимах: `Deny` остаётся отказом, на `Confirm` приходят кнопки,
`AskUserQuestion` показывается всегда.

### 5.7 Правила «Всегда»

| Инструмент | Что сохраняется | Когда подходит | Когда кнопки нет |
|---|---|---|---|
| Bash | первое слово и первый аргумент, например `go test` | команда равна шаблону или начинается с `шаблон + " "` и не содержит `; & | \` перевода строки < > $(` | в команде есть эти символы; первое слово — shell, интерпретатор (`python*`, `node`, `perl` …), разрушительная команда или обёртка (`rm`, `dd`, `chmod`, `find`, `env`, `xargs`, `sudo`, `ssh` …); префикс `VAR=value`; `git` с опцией перед подкомандой |
| Edit / MultiEdit / Write / NotebookEdit | абсолютная папка файла | файлы прямо в этой папке (не в подпапках), тот же инструмент | нет пути или запись чувствительная |
| Прочие | только имя инструмента | любые аргументы этого инструмента | — |

Правила действуют в пределах проекта и не истекают. Команды для просмотра
или удаления нет: они лежат в таблице `permission_rules`.

### 5.8 sudo

`SUDO_MODE`:

| Режим | Откуда пароль |
|---|---|
| `off` (по умолчанию) | Команды с sudo отклоняются с просьбой выполнить их вручную. На Windows включается принудительно. |
| `env` | `SUDO_PASSWORD` из `.env`. |
| `telegram` | Спрашивается в теме сессии; ответ пользователя сразу удаляется (нужно право «Удаление сообщений»; без него `tgsync check` выдаёт ошибку). |

Что происходит при одобрении sudo-команды (кнопкой или режимом 🟢):

1. Создаётся случайный одноразовый токен (128 бит). Каждый вызов sudo в
   команде переписывается в `TGSYNC_SUDO_TOKEN=<токен> sudo -A …`; флаги
   `-n`, `--non-interactive`, `-S`, `--stdin` (и внутри связок коротких
   флагов) удаляются. Переписанная команда заменяет исходную.
2. Регистрируется допуск: тема сессии, число вызовов sudo, срок 5 минут.
3. В окружении агента (задаётся при старте процесса) есть
   `SUDO_ASKPASS=<бинарник tgsync>`, `TGSYNC_ASKPASS=1`,
   `TGSYNC_ASKPASS_SOCK=<сокет>`. sudo запускает бинарник tgsync как askpass;
   тот отправляет `token <токен>` в unix-сокет и печатает полученный пароль.
4. Сервер проверяет вызывающего: на Linux (`SO_PEERCRED`, `/proc`) и macOS
   (`LOCAL_PEERPID`, `sysctl`) его родитель должен быть процессом с именем
   `sudo` и эффективным uid 0. На других системах проверки нет (при старте
   пишется предупреждение).
5. Каждый новый процесс sudo расходует одно использование допуска; один и
   тот же процесс sudo может спросить до 3 раз (опечатка в пароле). В режиме
   `telegram` запросы одной команды идут по очереди, а следующие вызовы sudo
   той же команды берут уже полученный ответ, если их собственный прошлый
   ответ не был неверным. Запрос пароля ждёт до 5 минут.
6. Когда ход заканчивается (или процесс завершается, или сессия закрывается),
   все допуски и открытый запрос пароля в теме отзываются.

Сокет: `<папка ноды>/askpass.sock` с правами 0600 или
`<temp>/tgsync-<хэш>.sock`, если путь получился бы длиной ≥100 байт. Пароль
никогда не попадает в окружение или контекст агента. Сообщение, начинающееся
с `/`, паролем не считается.

### 5.9 Пределы модели (обязательно к прочтению)

- **Автоматические режимы — не граница безопасности.** В режимах 🟢 и 🟡
  агент может выполнить любой код от пользователя ОС, под которым работает
  нода. Такой код может прочитать `.env` (токен бота, пароль sudo в режиме
  `env`), базу и всё, что может прочитать этот пользователь. Буквальная
  проверка, разбор команд и проверка обращений лишь требуют нажатия для
  очевидных написаний.
- tgsync видит только те вызовы, которые CLI передаёт в `CanUseTool`.
  Вызовы, которые CLI разрешает сам (его режим, например `acceptEdits`,
  правила allow в настройках Claude Code, чтение, которое он разрешает без
  вопроса), tgsync не проверяет.
- `profiles.yaml` и сокет askpass лежат в папке tgsync, но в список
  защищённых не входят; проверка обращений закрывает доступ к папке из Bash,
  но запись файловым инструментом за пределами проекта — обычный `Ask`.
- При `SUDO_MODE=env` пароль с правами root лежит на диске в `.env`.
- Любой, кто может писать в группу от имени разрешённого пользователя,
  управляет нодой.

## 6. Итоги хода (git-снимки)

### 6.1 Снимки

`files.Snapshot(dir)`:

1. Если `dir` не внутри рабочего дерева git, возвращается `""` (кнопок итога
   не будет).
2. Индекс репозитория копируется во временный файл (сохраняется stat-кэш
   git), `GIT_INDEX_FILE` указывает на него, в папке проекта выполняются
   `git --literal-pathspecs add -A -- .` и `git write-tree`. Хэш дерева и
   есть снимок. Индекс пользователя, ссылки, stash и рабочее дерево не
   меняются. Игнорируемые файлы не попадают; добавляется только папка
   проекта.
3. У каждого вызова git таймаут 30 с.

Снимок делается в начале хода (и для продолжений). В конце хода второй
снимок делается, только если ход менял файлы.

### 6.2 Изменённые файлы и статистика

- Изменённые файлы собираются из вызовов `Write`, `Edit`, `MultiEdit` и
  `NotebookEdit` с путём внутри проекта. Изменения, сделанные командами Bash,
  не учитываются.
- Сообщение итога: `📎 Изменено за ход: N · +A −D`, затем до 10 файлов с
  `+a −d`, `(новый)`, `(удалён)` или `(бинарный)` и ✓, если версия
  отправлялась. Цифры — из `git diff --numstat` / `--name-status`
  (`--no-renames --relative`) между двумя снимками.
- Если статистика есть, кнопки: 🔀 Diff, ✅ Коммит, ↩ Откатить. Живые кнопки
  есть у последних 5 итогов каждой сессии.

### 6.3 Diff

`git diff --no-renames --relative <base> <end> -- <файлы>` по файлам из
списка без защищённых; отправляется файлом `turn-<n>.diff` (≤50 МБ).
Работает для любого из последних 5 итогов.

### 6.4 Коммит

Сам tgsync не коммитит. Кнопка отправляет агенту сообщение: закоммитить
файлы из списка; хэш исходного дерева, чтобы `git diff <base> -- <файл>`
показывал только правки этого хода; спросить пользователя о более ранних
незакоммиченных правках в тех же файлах; сообщение — в стиле репозитория.
Один раз на итог, только для последнего хода простаивающей сессии.

### 6.5 Откат

- Только для последнего хода, только когда сессия простаивает и входящие
  пусты; требует подтверждения (Да, откатить / Нет).
- Пока идёт откат, ход не начинается; продолжение ждёт его окончания.
- Делается текущий снимок. Для каждого файла:
  - отличается между снимком конца хода и текущим (изменён после хода) →
    остаётся как есть, об этом сообщается;
  - создан в ходе → удаляется (вместе с опустевшими родительскими папками),
    если только в ходе не менялся `.gitignore` — тогда файл остаётся, об
    этом сообщается;
  - изменён, удалён или сменил тип → `git restore --source=<base>
    --worktree -- <файл>`;
  - нет в diff и git его игнорирует → сообщается как пропущенный.
- Индекс не трогается. Операция останавливается на первой ошибке.
- К следующему промпту агента добавляется пометка со списком откаченных
  файлов.

## 7. Файлы

### 7.1 Отправка файлов пользователю

Все отправки идут через `files.Read`:

- путь должен вести внутрь проекта; цель символической ссылки тоже должна
  быть внутри проекта;
- защищённые файлы не отправляются;
- только обычные файлы, не больше 50 МБ (лимит Bot API на загрузку);
- файл открывается без следования по конечной ссылке и без блокировки на
  FIFO (`O_NOFOLLOW | O_NONBLOCK` в Unix), дескриптор должен указывать на
  тот же файл, что проверялся; читается не больше 50 МБ.

Источники:

| Источник | Поведение |
|---|---|
| Инструмент `send_file` | С подписью; пропускается, если эта же версия (SHA-256) уже отправлялась в сессии. |
| Конец хода: упомянутые документы | Файлы, изменённые в сессии, чей путь есть в финальном ответе и чьё расширение — `.md .markdown .txt .pdf .html .htm .csv .png .jpg .jpeg .svg`. |
| Конец хода: `AUTO_SEND_GLOBS` | Изменённые в ходе файлы, подходящие под маску; префикс `**/` — «в любой папке». |
| `/file <путь>` | Отправляется, даже если уже отправлялся. |
| Кнопка файла в `/ls` | Отправляется, даже если уже отправлялся. |

Автоматически за ход отправляется не больше 5 файлов.

### 7.2 Обзор файлов `/ls`

- Показывает папку проекта (по умолчанию корень): сначала папки, затем файлы
  с размерами; 30 записей на страницу, кнопки «⬆ ..» и «➡ ещё».
- Скрыты `.git`, `node_modules`, `.venv`, `__pycache__` и защищённые файлы.
- Путь (с учётом ссылок) должен вести внутрь проекта.
- Переходы редактируют сообщение на месте. Живые кнопки есть у последних 5
  сообщений `/ls` каждой сессии.

### 7.3 Файлы от пользователя

- Документы и фото (наибольший размер, сохраняется как `photo.jpg`) в теме
  сессии; в теме управления не принимаются.
- Лимит Bot API на скачивание — 20 МБ; файл больше отклоняется с
  сообщением.
- Сохраняется как `<проект>/.tgsync/inbox/ГГГГММДД-ччммсс-<безопасное имя>`
  (папка 0700, файл 0600). В имени остаются буквы, цифры, `.`, `-`, `_`, не
  длиннее 100 символов.
- Если у проекта есть папка `.git`, в `.git/info/exclude` добавляется
  `.tgsync/`.
- С подписью: подпись сразу уходит агенту вместе со списком файлов. Без
  подписи: нода сообщает о файле и прикладывает его к следующему сообщению
  пользователя как «Пользователь прислал файлы …».

## 8. Голосовые сообщения

- Включаются, если задан `STT_URL`. Используется только собственный
  OpenAI-совместимый сервер (compose-файл для speaches/faster-whisper лежит в
  `deploy/stt/compose.yaml`, слушает `127.0.0.1:8000`).
- Принимаются голосовые и аудиофайлы в теме сессии. Отклоняются: в теме
  управления, длиннее `STT_MAX_SECONDS` (по умолчанию 300), больше 20 МБ.
- Запрос: `POST <STT_URL>/v1/audio/transcriptions`, multipart с `file`,
  `model` (`STT_MODEL`) и `response_format=json`; тело ответа читается до
  1 МБ; используется поле `text`.
- Таймауты: `STT_TIMEOUT` (по умолчанию 60 с) ограничивает скачивание вместе
  с распознаванием; таймаут HTTP-клиента — `STT_TIMEOUT`, а при 0 — 2 минуты.
- Распознанный текст (≤3500 символов) показывается в раскрывающейся цитате.
  Если вопрос ждёт «✍ Свой ответ», текст становится ответом. Иначе агент
  получает текст с пометкой, что в распознавании возможны ошибки, подпись
  (если есть) и указание пересказать задачу в одном-двух предложениях и
  дождаться подтверждения.
- Распознавание идёт в обработчике темы: сообщения, присланные в эту тему в
  это время, обрабатываются после него.

## 9. Управление группой

### 9.1 Права

- При старте нода читает свои права администратора (`getChatMember`). Без
  права **«Управление темами»** нода не запускается.
- Необязательные права и что они дают:

| Право | Для чего |
|---|---|
| Закрепление сообщений | закрепить карточку |
| Изменение профиля группы | аватар и описание группы |
| Удаление сообщений | удаление пустых тем, 🧹 уборка, чистка темы управления, удаление сообщения с паролем sudo |

- О недостающих необязательных правах нода один раз пишет в тему
  управления; повторно — только если набор недостающих прав изменился
  (`kv.missing_rights`).

### 9.2 Разовая настройка группы

- Загружаются стикеры иконок тем (`getForumTopicIconStickers`) и
  сопоставляются ролям: активна 💻/🤖/💬, закрыта ✅/✔/👍/🏁, упала ❌/❗/‼/⚠.
- General скрывается один раз для базы (`kv.general_hidden`); если
  пользователь снова его покажет, он останется видимым.
- Если бот может менять профиль группы, а у группы нет фото или описания,
  один раз ставятся встроенные аватар и описание (`kv.group_profile_done`).
- Цвет тем — один из шести цветов Telegram, выбирается по хэшу имени ноды.

### 9.3 Тема управления и карточка

- `EnsureControl` переименовывает сохранённую тему в `🖥 <нода>`; если
  Telegram отвечает, что темы нет, создаётся и сохраняется новая. `/control`
  в General делает то же и отвечает ссылкой.
- Карточка редактируется на месте; если её сообщения нет, отправляется и
  тихо закрепляется новое; если нет самой темы, сначала она создаётся заново.

### 9.4 Чистка темы управления и меню

- Сообщения бота в тему управления, отправленные через роутер, и сообщения
  пользователя в ней записываются в `control_msgs`. Каждую минуту записанные
  сообщения старше часа удаляются. Если удалить нельзя (уже удалено или
  слишком старое для Bot API), сообщение забывается; после временной ошибки
  попытка повторяется. Одна чистка длится не больше минуты.
- 🧽 Очистить тему удаляет все записанные сообщения сразу.
- Новое сообщение с кнопками в теме управления удаляет предыдущее (остаётся
  только последнее меню; `kv.control_menu_msg`).
- Карточка и уведомление о правах не удаляются никогда.

### 9.5 Темы сессий

- Создаются с цветом ноды и иконкой активной сессии.
- Переименовываются один раз: из `новая сессия` в первую строку первого
  сообщения.
- При закрытии: тема без записанного расхода и без id сессии Claude
  удаляется (если удалить не вышло — закрывается); иначе получает иконку
  закрытой и закрывается. Название при закрытии не меняется (каждое
  переименование добавляет в тему служебное сообщение).
- Состояние failed ставит иконку ошибки; при выходе из него возвращается
  иконка активной сессии.

### 9.6 🧹 Уборка

Кандидаты: закрытые сессии, чьи темы ещё существуют, и упавшие сессии без
единого записанного хода. Кнопка показывает до 10 из них и просит
подтверждения; после подтверждения список читается заново, каждая тема
удаляется (`deleteForumTopic`), помечается `topic_deleted_at`, загруженная
сессия для неё выгружается. Результат пишется в то же сообщение, карточка
обновляется.

## 10. Хранение данных

### 10.1 База

SQLite через `modernc.org/sqlite` (чистый Go), открывается с
`journal_mode(WAL)`, `busy_timeout(5000)` и одним соединением. Папка
создаётся с правами 0700. Путь по умолчанию — `./data/tgsync.db`
относительно папки ноды.

| Таблица | Основные столбцы | Назначение |
|---|---|---|
| `kv` | `key` PK, `value` | Небольшие настройки ноды (ниже). |
| `sessions` | `id` PK, `thread_id` UNIQUE, `project`, `cwd`, `title`, `claude_session_id`, `state`, `mode`, `profile`, `topic_deleted_at`, `created_at`, `updated_at` | Строка на каждую тему сессии. |
| `permission_rules` | PK (`project`, `tool`, `pattern`), `created_at` | Правила «Всегда». |
| `usage` | `id` PK, `at` (unix, мс), `thread_id`, `project`, `model`, `input`, `output`, `cache_read`, `cache_create`, `cost` | Расход по ходам и моделям. Индексы по `at` и `thread_id`. |
| `rate_limits` | `name` PK, `status`, `utilization`, `resets_at`, `updated_at` | Последнее известное состояние каждого окна лимита. |
| `control_msgs` | `msg_id` PK, `sent_at` | Сообщения темы управления, которые нужно удалить. |

Ключи `kv`: `control_thread_id`, `approve_mode`, `control_card_msg`,
`control_menu_msg`, `general_hidden`, `group_profile_done`, `missing_rights`.

### 10.2 Миграции

Схема создаётся через `CREATE TABLE IF NOT EXISTS`. Миграции — список
`ALTER TABLE … ADD COLUMN`, который выполняется при каждом старте; ошибки
«duplicate column» игнорируются. Сейчас миграции добавляют
`sessions.profile` и `sessions.topic_deleted_at`.

### 10.3 Что переживает перезапуск

| Сохраняется | Теряется |
|---|---|
| Сессии и их темы, id сессий Claude, режимы, профили | Работающие процессы Claude (продолжатся со следующим сообщением) |
| Режим автоодобрения, правила «Всегда» | Сообщения во входящих, ещё не отправленные агенту |
| Расход, окна лимитов и учёт отправленных уведомлений | Открытые запросы разрешений и вопросы (их кнопки отвечают «Запрос устарел») |
| Тема управления, id карточки и меню, список для чистки | Кнопки итогов хода, `/ls`, панели субагентов, списки `/history` |
| Флаги настройки группы | Допуски sudo, снимки контекста, хэши отправленных файлов |

## 11. Работа с Telegram API

### 11.1 Методы

`getUpdates` (long polling), `getMe`, `getChat`, `getChatMember`,
`sendMessage`, `editMessageText`, `editMessageReplyMarkup`, `deleteMessage`,
`setMessageReaction`, `pinChatMessage`, `sendDocument`, `getFile` (и ссылка
на скачивание файла), `createForumTopic`, `editForumTopic`,
`closeForumTopic`, `deleteForumTopic`, `hideGeneralForumTopic`,
`getForumTopicIconStickers`, `setChatPhoto`, `setChatDescription`,
`setMyCommands` (в области группы), `answerCallbackQuery`. Подкоманда
`profile` также использует `setMyShortDescription`, `setMyDescription` и
`setMyProfilePhoto`.

Все сообщения — в режиме HTML, предпросмотр ссылок выключен.

### 11.2 Ошибки, повторы, запасной вариант

- **Разбор ошибок:** 429 → `RetryError` с `retry_after`; ошибка соединения
  (dial) → повторяемая и безопасная; прочие сетевые/URL-ошибки →
  повторяемые, но *небезопасные* (запрос мог дойти); «message thread not
  found», `TOPIC_ID_INVALID`, `TOPIC_DELETED` → `ErrTopicGone`; «message to
  edit not found», `MESSAGE_ID_INVALID` → `ErrMessageGone`; «not modified» →
  успех.
- **`Resilient`** оборачивает API, которым нода пользуется после старта.
  Повторяет `RetryError` с `retry_after` или с экспоненциальной паузой (1 с,
  удваивается до 30 с) в пределах общего бюджета: 5 минут для отправки
  сообщений и документов, создания/закрытия/удаления тем и удаления
  сообщений; 30 с для правок и смены иконок. Создающие вызовы (сообщение,
  документ, тема) после небезопасной ошибки не повторяются, чтобы не было
  дублей. `answerCallbackQuery`, реакции, закрепление, скачивание и
  `getChatMember` не повторяются.
- **Запасной вариант при ошибке разметки:** если Telegram отклоняет HTML
  («can't parse entities»), сообщение, правка или подпись отправляются
  заново простым текстом без тегов и с раскрытыми сущностями.
- **Удалённая тема:** любая `ErrTopicGone` при работе с сессией закрывает
  сессию (§14).

### 11.3 Ограничения размеров

| Ограничение | Значение |
|---|---|
| Текст сообщения | 4096 символов; ответы делятся на HTML-части ≤4000 символов, длинные строки режутся по 800 символов; незакрытый блок кода закрывается и открывается заново в следующей части |
| Ответ + строка итога | объединяются в одно сообщение, если последняя часть, строка итога и 40 символов запаса помещаются в 4096 |
| Данные кнопки | 64 байта (кнопки проектов, чьи данные не помещаются, не показываются) |
| Всплывающее уведомление кнопки | 200 символов (ошибки режутся до 190) |
| Имя темы | 128 единиц UTF-16, обрезается с «…» |
| Заголовок сессии | первая строка первого сообщения, 40 символов |
| Загрузка | 50 МБ |
| Скачивание | 20 МБ |

### 11.4 Префиксы данных кнопок

| Префикс / формат | Где | Значение |

## 12. Справочник настроек

Папку ноды выбирает `FindHome`: `TGSYNC_HOME`, если задан (папка должна
существовать); иначе первая из текущей папки, `~/.config/tgsync` и
`<папка настроек пользователя>/tgsync` (`%AppData%` на Windows,
`~/Library/Application Support` на macOS), где есть `.env`; иначе текущая
папка. Процесс переходит в эту папку, загружает из неё `.env` (его может не
быть; переменные, уже заданные в окружении, не перезаписываются) и читает
`profiles.yaml`. Все ошибки настроек выводятся сразу вместе.

| Переменная | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `TELEGRAM_BOT_TOKEN` | строка | — (обязательна) | Токен бота ноды. Удаляется из окружения процесса после загрузки. |
| `ALLOWED_USER_IDS` | положительные int64 через запятую | — (обязательна) | Id пользователей Telegram, которым разрешено управлять нодой, например `123456789`. |
| `GROUP_CHAT_ID` | отрицательное int64 | — (обязательна) | Супергруппа с темами, например `-1001234567890`. |
| `NODE_NAME` | строка | hostname | Имя ноды в названии темы управления и на карточке. |
| `PROJECTS_ROOT` | абсолютный путь | — (обязательна) | Папка с проектами, например `/home/user/projects`. |
| `DB_PATH` | путь | `./data/tgsync.db` | База SQLite. |
| `MAX_PARALLEL_SESSIONS` | целое ≥1 | `3` | Сколько ходов одновременно на ноде (и не больше одного на проект). |
| `AUTO_SEND_GLOBS` | маски через запятую | пусто | Изменённые файлы, отправляемые в конце хода; `**/` — в любой папке. |
| `IDLE_TIMEOUT` | длительность, `0` — никогда | `2h` | Остановить простаивающий процесс Claude; следующее сообщение продолжит сессию. |
| `STALL_WARN` | длительность, `0` — выкл. | `20m` | Предупредить, если в ходе нет активности (не во время ожидания пользователя). |
| `REMIND_EVERY` | длительность, `0` — выкл. | `2h` | Напоминать о неотвеченных запросах и вопросах. |
| `MAX_TURN_DURATION` | длительность, `0` — без лимита | `0` | Прерывать ходы длиннее этого. |
| `DEFAULT_PROFILE` | строка | `full` | Профиль, если его не задали ни `--profile`, ни проект. |
| `SHOW_HOOK_OUTPUT` | `true/1/yes` или `false/0/no` | `true` | Показывать `systemMessage` hooks и их сбои. |
| `SUDO_MODE` | `off` / `env` / `telegram` | `off` | Политика sudo (§5.8). На Windows всегда `off`. |
| `SUDO_PASSWORD` | строка (пробелы не обрезаются) | пусто | Пароль для `SUDO_MODE=env` (там обязателен). Удаляется из окружения процесса после загрузки. |
| `STT_URL` | `http(s)://хост[:порт]` | пусто (голосовые выкл.) | Адрес собственного сервера распознавания речи. |
| `STT_MODEL` | строка | `Systran/faster-whisper-small` | Имя модели для сервера STT. |
| `STT_TIMEOUT` | длительность, `0` — без дедлайна контекста | `60s` | Ограничение на скачивание и распознавание одного голосового. |
| `STT_MAX_SECONDS` | целое ≥1 | `300` | Самое длинное принимаемое голосовое. |
| `CLAUDE_CLI_PATH` | путь | пусто (`claude` из `PATH`) | Путь к Claude Code CLI. |
| `TGSYNC_HOME` | путь | — | Явная папка ноды (читается до `.env`). |
| `TGSYNC_LOG` | путь | — | Дописывать stderr и логи в этот файл (используется задачей Windows). |
| `CLAUDE_CONFIG_DIR` | путь | `~/.claude` | Откуда `/history` читает журналы Claude Code. |

Длительности — в синтаксисе Go (`30s`, `20m`, `2h`). Служебные переменные,
которые нода задаёт агенту: `SUDO_ASKPASS`, `TGSYNC_ASKPASS`,
`TGSYNC_ASKPASS_SOCK`, `TGSYNC_SUDO_TOKEN`.

Формат `profiles.yaml`:

```yaml
profiles:
  lean:
    setting_sources: [user, project, local]   # пусто → user, project, local
    env: { SOME_VAR: "value" }
    settings: { enabledPlugins: { "example@example": false } }
projects:
  some-project:
    profile: lean
```

Фиксированные внутренние значения: интервал правки статуса 3 с; проверка тем
раз в 10 мин; обновление карточки раз в 10 с; чистка раз в минуту для
сообщений старше часа.

## 14. Сбои и восстановление

| Ситуация | Поведение |
|---|---|
| Перезапуск ноды | `Restore` загружает все незакрытые сессии. Сессии не в состоянии `idle`, `failed` или `interrupted` становятся `interrupted` с уведомлением. Процесс Claude не запускается до следующего сообщения, которое продолжает сессию по id. |
| Процесс Claude завершился во время хода | Открытые запросы и допуски sudo темы снимаются, работающие субагенты помечаются остановленными, отложенный текст публикуется, состояние `failed` с уведомлением. Сообщения из очереди снова планируются; следующее сообщение запускает новый процесс с продолжением сессии. |
| Claude не запустился / промпт не отправился | Сообщение возвращается в начало входящих, состояние `failed`, уведомление «Сообщение сохранено и уйдёт вместе со следующим». |
| Простаивающий процесс | Останавливается через `IDLE_TIMEOUT` (не пока работают субагенты); продолжается со следующим сообщением. |
| Долгая тишина / долгий ход | Уведомление `STALL_WARN` с ⏳/⏹; `MAX_TURN_DURATION` прерывает ход (если прервать не удалось, попытка повторится на следующем тике). |
| Тема сессии удалена | Обнаруживается на любом вызове Telegram (`ErrTopicGone`) или проверкой простаивающих сессий раз в 10 минут (повторная установка того же имени темы). Сессия закрывается: процесс и субагенты останавливаются, запросы снимаются, состояние `closed`, ставится `topic_deleted_at`. |
| Тема управления удалена | Создаётся заново при обновлении карточки (примерно в течение минуты) или по `/control` в General. |
| Карточка удалена | При следующем обновлении отправляется и закрепляется новая. |
| Telegram недоступен или ограничивает частоту | `Resilient` ждёт и повторяет в пределах бюджета (§11.2); события агента тем временем копятся в буферах. После исчерпания бюджета вызов завершается ошибкой и пишется в лог; этот вывод теряется. Long polling переподключается сам. |
| Паника в обработчике | Перехватывается диспетчером и пишется в лог со стеком; нода продолжает работу. Паники в других горутинах не перехватываются и завершают процесс; его перезапускает менеджер сервисов. |
| Остановка (SIGINT/SIGTERM) | Процессы Claude закрываются; состояния сессий сохраняются, поэтому при следующем старте шедшие ходы становятся `interrupted`. Второй сигнал завершает процесс сразу. |
| Два процесса с одним токеном | Telegram отвечает 409 на polling; скрипты установки отказываются устанавливать, пока работает другой `tgsync`. |

## 15. Платформы и сборка

### 15.1 Сборка

- Go **1.27.1** (из `go.mod`); `CGO_ENABLED=0` (SQLite на чистом Go).
- `make build` → `bin/tgsync`; `make test` запускает `go test -race ./...`;
  `make it` — интеграционные тесты на реальном авторизованном `claude`.
- Релизы (goreleaser): linux, darwin, windows × amd64, arm64; в архивах
  `README.md`, `LICENSE`, `.env.example`, `profiles.example.yaml`, `docs/*`,
  `scripts/*`.
- Для работы нужны: авторизованный Claude Code CLI и `git` в `PATH`
  (снимки, создание проектов, откат).

### 15.2 Платформы

| Платформа | Сервис | Папка ноды | Особенности |
|---|---|---|---|
| Linux | пользовательский юнит systemd `tgsync.service` (`scripts/install.sh`): `Restart=on-failure`, `RestartSec=5`, `TimeoutStopSec=20`; `loginctl enable-linger`, чтобы работать без входа в систему | `~/.config/tgsync` | Бинарник в `~/.local/bin`. `.env` 0600, папки 0700. Проверка вызывающего через `/proc`. |
| macOS | агент launchd `dev.tgsync` (`scripts/install.sh`): `RunAtLoad`, `KeepAlive` при ненулевом коде выхода, пауза 5 с | `~/Library/Application Support/tgsync` | Логи в `~/Library/Logs/tgsync.log`. Работает, пока пользователь в системе. Проверка вызывающего через `sysctl`. |
| Windows | задача планировщика `tgsync` при входе (`scripts/install.ps1`), скрытый цикл PowerShell перезапускает через 5 с при ненулевом коде выхода | `%AppData%\tgsync` | Бинарник в `%LocalAppData%\tgsync\bin`; логи через `TGSYNC_LOG`. sudo всегда выключен. Проверки путей без учёта регистра и с формами Windows/Git Bash. Работает, пока пользователь в системе. |
| Docker | `Dockerfile` (сборка на Go; образ `node:22-bookworm-slim` с Claude Code из npm, git, python3) и `docker-compose.yml` (`restart: unless-stopped`) | `/config` (`TGSYNC_HOME`) | Работает с uid/gid пользователя хоста; монтирует `~/.config/tgsync`, `~/.claude`, `~/.claude.json` и `PROJECTS_ROOT` по тем же путям, что на хосте. sudo в контейнере нет; оставьте `SUDO_MODE=off`. ноды; выполняют `tgsync check` перед регистрацией сервиса.

## 16. Ограничения и известные проблемы

- **Цена снимков.** Неотслеживаемых файлов нет в stat-кэше копии индекса,
  поэтому каждый снимок заново хэширует все неотслеживаемые и
  неигнорируемые файлы папки проекта: дважды за ход, менявший файлы, и один
  раз за остальные. Большие неотслеживаемые файлы замедляют ходы.
- **Учёт изменённых файлов** видит только `Write`/`Edit`/`MultiEdit`/
  `NotebookEdit`. Файлы, изменённые командами Bash (генераторы, `sed -i`,
  форматтеры), не попадают в итог хода, не отправляются автоматически и не
  откатываются.
- **Брошенные запросы разрешений.** Запрос остаётся открытым, пока на него не
  ответят, не закончится ход, не завершится процесс или не закроется сессия.
  Если CLI бросает отдельный запрос посреди хода, его сообщение сохраняет
  живые кнопки до конца хода; нажатие на них на агента уже не влияет.
- **После перезапуска ноды** запросы, опубликованные до него, сохраняют
  кнопки; нажатие лишь отвечает «Запрос устарел».
- **История читает только хвост.** `/history` берёт пользовательский
  заголовок и последний промпт из последних 256 КиБ каждого журнала;
  результат субагента — из последних 8 МиБ его журнала. Более ранние
  значения за пределами этих окон не видны.
- **Один ход на проект.** Две сессии одного проекта никогда не выполняют
  ходы одновременно, даже при свободных слотах.
- **Правила «Всегда»** нельзя посмотреть или удалить из Telegram.
- **Чувствительные записи** в режимах 🟢/🟡 разрешаются автоматически (это
  `Ask`, а не `Confirm`).
- **Не весь вывод в теме управления чистится.** `/usage` и уведомления о
  лимитах отправляются в тему управления без обёртки чистки, поэтому через
  час не удаляются и не заменяют предыдущее меню.
- **У уборки нет порога возраста.** К удалению предлагается любая закрытая
  сессия с существующей темой, включая закрытую минуту назад.
- **Проверка вызывающего** есть только на Linux и macOS; на других системах
  защищают только одноразовый токен и права на сокет (на Windows sudo
  выключен).
- **Ограничения Telegram:** скачивание до 20 МБ, загрузка до 50 МБ,
  сообщения старше 48 часов бот удалить не может (чистка их забывает).
- **MCP-серверы с OAuth** нельзя авторизовать из сессии бота; пользователю
  предлагается сделать это в интерактивном `claude`.
- **Голосовые** блокируют очередь сообщений темы на время распознавания.
- **Вне перехвата паник:** чтение событий сессий и тикеры; паника там
  перезапускает всю ноду через менеджер сервисов.
